#### Hardware Bring-up: USART1 DMA cache, rate-group, and queue-depth fixes (September 2, 2026)

#### Swappable driver architecture: host-native unit testing for STM32 drivers (September 14, 2026)
*Goal: Make `fprime-util check` actually work for `Stm32GpioDriver`, `Stm32UartDriver`, and `STM32Timer` — previously impossible, since every driver `#include`d real Cube HAL/CMSIS headers that only compile under `arm-none-eabi-gcc`, and the whole `lib/fprime-stm32` tree (including the real HAL static library) was pulled into every build unconditionally, including host UT builds.*
*   [x] **Adopted F´'s own swappable-driver convention** (the same `Common`/`Real`/`Stub` source split already used by `lib/fprime/Drv/LinuxGpioDriver`/`LinuxI2cDriver`/`LinuxSpiDriver`) instead of hand-authoring fake vendor headers, so the pattern is immediately recognizable to any F´ contributor and carries zero risk of a fake header drifting from real HAL semantics. Each driver now has three source files sharing one HAL-free header: `<Driver>Common.cpp` (hardware-independent logic — ring buffers, validation, state machines, event/telemetry emission — built on every platform), `<Driver>.cpp` (the real HAL-touching implementation, `stm32h7` target only), and `<Driver>Stub.cpp` (fixed-behavior stand-in with zero HAL/CMSIS dependency, host UT only).
*   [x] **Stripped every vendor CMSIS/HAL type out of driver headers:** `Stm32GpioDriver::open()` now takes a project-defined `Stm32::GpioPort` enum instead of a raw `GPIO_TypeDef*` (mapped to the real peripheral base only inside the real `.cpp`); `Stm32UartDriver::open()`'s `IRQn_Type` parameter widened to a plain `I32`. Register/HAL access that can't be trivially abstracted (DMA completion, ISR callbacks with no user-context pointer) is routed through small `hw*()` boundary methods and public `signalX()`/`signalTick()` methods a unit test can call directly to simulate the hardware event, backed by a single-instance callback trampoline in the real `.cpp` only.
*   [x] **Root-caused and fixed a `restrict_platforms()` /`register_fprime_ut()` interaction bug:** `restrict_platforms()` is a CMake *macro*, so its `return()` on a platform mismatch exits the *entire including file* — placing it above an unconditional `register_fprime_ut()` call (the initially-drafted design) silently prevented the UT target from ever being registered on host, surfacing as `fpp-depend cache did not generate` / a missing UT target rather than a clear error. Fixed by making `register_fprime_module()`/`register_fprime_library()` production registration always execute (never returning out of the file), varying only which source file (`<Driver>.cpp` vs `<Driver>Stub.cpp`) and `DEPENDS` are selected via a plain `if(FPRIME_PLATFORM STREQUAL "stm32h7" AND NOT FPRIME_USE_STUBBED_DRIVERS)`.
*   [x] **Gated the real vendor HAL library and the ARM-only deployment to the `stm32h7` platform:** `lib/fprime-stm32/CMakeLists.txt`'s `FprimeStm32` static library (and its `Os/` subdirectory) and `FprimeBaremetalReference/Deployments/ReferenceDeployment/CMakeLists.txt` (STM32H753XI linker script, Cortex-M startup assembly) are now both restricted to `stm32h7`, so a host-native `fprime-util generate`/`check` never hands vendor HAL `.c` sources or the ARM-only deployment to the host compiler. Added a small always-registered `FprimeStm32Config` interface target so drivers can still read plain-numeric config headers (e.g. `UartDriverConfig.hpp`) on every platform without depending on the gated `FprimeStm32` target.
*   [x] **Verified the fix doesn't regress the flight build:** `fprime-util generate stm32h7` + `fprime-util build stm32h7` still configures, compiles, and links the full `ReferenceDeployment` ELF unchanged, confirming the host-UT-enabling refactor is behavior-preserving on the real target.
*   [x] **Caught a real driver bug via the new tests:** `Stm32UartDriver`'s `TxErrorCount`/`RxErrorCount` telemetry channels were declared in FPP but never written from `run_handler` — found while writing the UART error-recovery unit test, fixed in `Stm32UartDriverCommon.cpp`.

#### Week 10: I2C driver architecture and polled transfer baseline
*Goal: Add a reusable F´ passive I2C driver component to `lib/fprime-stm32`, with deterministic, bounded transaction handling and no application-level HAL access.*
*   [x] **Enable and configure an STM32H7 I2C peripheral:** Enabled I2C1 (PB6/PB7 SCL/SDA, open-drain, CubeMX-generated clock/GPIO/MSP config in `lib/fprime-stm32/src/i2c.c`/`include/i2c.h`). `open(instance, busSpeed)` selects both the peripheral instance (`Stm32::I2cInstance::I2c1`, with `I2c2`/`I2c3`/`I2c4` declared — but not yet CubeMX-configured — for other boards) and a bus speed preset (`Stm32::I2cBusSpeed::Standard`/`Fast`/`FastPlus`; CubeMX-computed `Timing` register values for this project's actual D2PCLK1 clock, since the H7 I2C peripheral has no runtime baud-rate formula like UART does). *   [x] **Define the FPP component boundary — revised from the originally-planned async design:** Implemented `Stm32.Stm32I2cDriver` as a passive component importing the framework's `Drv.I2c` interface (guarded, synchronous `write`/`read`/`writeRead` ports, each returning `Drv::I2cStatus` directly to the caller) instead of a custom async request/completion-port pair. This makes the "single in-flight transaction" and "no dynamic queueing" goals automatic: each port call blocks for the duration of its own transaction, so there is nothing to admit, reject, or queue.
*   [x] **Bounded and deterministic, but polled rather than interrupt-driven:** Every `HAL_I2C_Master_Transmit`/`_Receive` call is blocking, bounded by a fixed 10 ms `TRANSACTION_TIMEOUT_MS` watchdog passed as the HAL's own `Timeout` parameter. `HAL_I2C_MspInit()` (`src/i2c.c`) only enables the I2C1 clock/GPIO — no NVIC event/error interrupt is enabled — so there is no ISR to keep minimal for now. `HAL_I2C_GetError() & HAL_I2C_ERROR_AF` distinguishes an address-phase NACK (`I2C_ADDRESS_ERR`) from a data-phase/bus failure (`I2C_WRITE_ERR`/`I2C_READ_ERR`) on every failed call. `writeRead` is two back-to-back blocking calls (STOP then START, not a single electrically-held repeated START) — a documented limitation (`docs/sdd.md`) safe on this single-master bus, but a sensor that strictly needs the bus held across the register-address write will need the sequential IT API with I2C1's NVIC interrupt enabled first.
*   [x] **Common/Real/Stub split, ready for host UT (no tests written yet):** Follows the same HAL-boundary convention as `Stm32UartDriver` (`lib/fprime-stm32/README.md`) — `Stm32I2cDriverCommon.cpp` (hardware-independent port handler logic), `Stm32I2cDriver.cpp` (real HAL boundary, `stm32h7` target only), `Stm32I2cDriverStub.cpp` (injectable/observable stand-in for host `fprime-util check`). `register_fprime_ut` is scaffolded but commented out in `CMakeLists.txt` since no `test/ut/` files exist yet.
